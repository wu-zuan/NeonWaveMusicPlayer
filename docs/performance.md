# 效能與資源管理

播放進度由進度條和開啟中的歌詞個別訂閱媒體事件；跳秒不再更新整個主畫面。所有歌曲的合併列表與搜尋索引只在歌曲資料變動時重建，搜尋輸入使用 React 延後計算，列表維持虛擬捲動。

## 記憶體與工作量上限

| 資源 | 上限／回收方式 |
| --- | --- |
| 列表封面快取 | 80 筆／16 MiB，先達到者優先；包含無封面的結果 |
| 主程序封面快取 | 200 筆／32 MiB，依使用順序淘汰 |
| 主程序歌曲資訊快取 | 10,000 筆／8 MiB，依音檔修改時間與大小重新驗證 |
| 歌詞快取 | 64 筆／4 MiB |
| 列表封面讀取 | 最多同時 2 個；離開畫面的待處理請求會取消 |
| 主程序音檔解析 | 最多同時 4 個；相同請求共用解析結果 |
| 資料夾檔案屬性讀取 | 最多同時 16 個 |

以上 MiB 是快取保留內容的估算預算，不是整個應用程式的記憶體上限。正在顯示的封面、Chromium 圖片解碼、音訊緩衝與其他功能各有額外占用。超出單筆預算的封面仍可顯示，但不保留在快取中；歌曲數量不受快取筆數限制。超過歌曲資訊快取容量的大型音樂庫，重新開啟時仍可能重新解析被淘汰的音檔。

8D 的旋轉計時器只在媒體播放且音訊環境運作時執行，暫停與結束會停止。殘響依需求產生並重用固定模式的緩衝，關閉後等待淡出再移除運算分支。播放器卸載時會釋放音訊圖、擷取串流、事件訂閱、計時器與媒體來源；React 開發模式的立即重掛載會保留並重用同一組資源。

暫停時停止週期性播放狀態同步，由切歌、跳轉、設定變更等事件觸發；迷你播放器啟動後會主動取得完整快照。完整歌曲的歌詞校正流程也避免對已經獨立的音訊 ArrayBuffer 再製作一份副本。

## 驗證

```bash
npm run typecheck
npm run test:performance
npm run test:party
npm run build:dir
npm run e2e:performance
```

效能回歸測試涵蓋快取淘汰、取消佇列、並行上限、資料更新、播放時鐘取消訂閱與音效資源釋放。桌面測試會使用獨立的臨時設定檔與合成音訊，驗證兩萬首歌曲列表、搜尋、播放與暫停。它不使用個人音樂庫或登入資訊。

原 Electron 版本在 2026-09-13 留存的歷史測試：21 項效能／回收測試與 23 項既有回歸測試通過。載入 20,000 筆合成歌曲資料時，列表起點、中段、末端分別掛載 22、33、23 列；播放時鐘觀察期間進度介面更新 9 次，MainApp 重繪 0 次。

同日最終 Tauri production / WebView2 在 Windows 10 LTSC 的驗證：上述 44 項測試及 3 項新增 native service / transport 測試通過。20,000 筆歌曲桌面測試的列表掛載數為 48、63、54，仍低於 80；1.4 秒觀察期間播放前進 1.401 秒，播放介面 commits 173 次，MainApp 重繪 0 次。搜尋後按 Enter、切換歌單、播放跳轉、8D 暫停／繼續、暫停中開啟迷你播放器的完整快照均通過。完整記錄位於 `artifacts/performance-validation.json`。

Tauri 截圖驗證透過 CDP 固定 viewport / focus，避免隱藏 WebView2 surface 遺漏 compositor layers；原歷史資料使用不同的 visibility / focus 條件。因此不能把兩次的列數或 commits 差值解讀成效能改善或退步。這是列表與播放行為測試，並非讀取兩萬個真實音檔的啟動速度基準。

7.0.9 發佈驗證另增加 2 項原生套件封裝測試，確認保留正確的平台／CPU 預建模組與 macOS universal binary，並排除 glibc AppImage 不使用的 musl 模組；目前共 49 項回歸測試。

7.1.0 修正列表量測造成的高度持續增長：改由有明確高度的 flex 容器分配標題與清單空間，react-window 觀察實際清單尺寸。搜尋定位在清單完成量測後更新，視窗／主題調整後也會保留目前的命中歌曲。先前測試只確認命中列已掛載及反白，無法發現歌曲仍在畫面外；桌面測試現在另外檢查高度穩定，以及五種主題在 1200 × 800、800 × 600 下的首筆、末筆及 Enter 循環結果是否完整顯示於播放列上方。

這些測試驗證資源管理與操作行為，不能推算每台電腦的 CPU 或記憶體改善百分比。長時間使用與真實封面、歌詞校正、Discord 串流的負載仍需依實際使用情境量測。
